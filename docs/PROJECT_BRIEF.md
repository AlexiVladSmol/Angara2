# Angara — описание продукта

Статус: **PROPOSED / требуется согласование владельца**. Дата предложения: 9 ноября 2026 года. Ревизия: 0.1.

## Назначение

Angara — самостоятельный прямой web proxy для Linux. Клиент явно настраивает адрес прокси. Сервер проверяет доступ и передаёт HTTP-запрос либо создаёт CONNECT-туннель. Ориентир по классу задач — Squid: проксирование, пользователи, ACL, наблюдаемость и дальнейшее кэширование.

Предлагаемый первый сценарий: один администратор разворачивает сервис на Linux-сервере и предоставляет авторизованным клиентам управляемый доступ к web-ресурсам. Требования корпоративной сети, личного сервера и массового публичного сервиса различаются; окончательный сценарий подтверждает владелец.

## Первый пригодный к эксплуатации выпуск v0.1

| ID | Требование | Результат для пользователя |
| --- | --- | --- |
| F01 | HTTP/1.1 explicit forward proxy | Обычные HTTP-запросы и загрузки через прокси |
| F02 | CONNECT с IPv4, IPv6 и DNS-именем | HTTPS и другие явно разрешённые TCP-туннели |
| F03 | HTTP- и HTTPS-listener | Возможность защитить соединение клиента с самим прокси TLS |
| F04 | Basic proxy authentication и локальные пользователи | Подключение по логину и паролю; ответ 407 при необходимости |
| F05 | ACL: источник, пользователь, домен, IP назначения, порт, метод | Администратор явно определяет разрешённый доступ |
| F06 | Лимиты и таймауты | Предсказуемое поведение при медленных клиентах и перегрузке |
| F07 | TOML-конфигурация и её отдельная проверка | Ошибки обнаруживаются до изменения работающего сервиса |
| F08 | JSON-журналы и базовые метрики | Диагностика соединений и отказов без раскрытия секретов |
| F09 | Graceful shutdown и согласованная перезагрузка настроек | Управляемое завершение и изменение ACL без повреждения состояния |
| F10 | Установка как systemd-сервис от отдельного пользователя | Воспроизводимое развёртывание и обновление |

Первый выпуск считается готовым после M08. Промежуточные сетевые этапы предназначены для локальной разработки и проверки.

## Предлагаемые границы

- Поддержка HTTP/1.1 на входе прокси и на исходящей HTTP-стороне. HTTP/2 сайта может проходить внутри непрозрачного CONNECT-туннеля.
- Для HTTPS-ресурсов клиент использует CONNECT. Поддержка absolute-form https URI отдельно не обещается в v0.1.
- Передача тела и туннеля потоковая: память не растёт пропорционально размеру загрузки.
- Локальное хранение хэшей паролей; работа с системными учётными записями, LDAP и Kerberos — отдельные расширения.
- Установка без обязательного Docker. Изолированные контейнеры допускаются для тестового стенда, если доступны в CI.
- В проекте будет собственный понятный формат конфигурации. Импорт squid.conf рассматривается позже как отдельный инструмент.
- Порт по умолчанию предлагается 3128; адрес первого запуска — loopback. Публичное прослушивание задаётся администратором явно.
- Источник истины — репозиторий, его Issues, PR и согласованные документы.

В v0.1 не включаются: SSL bump / перехват TLS сайтов, прозрачный proxy, reverse proxy, SOCKS5, UDP/QUIC proxy, ICAP/eCAP, GUI, кластер, внешняя БД и произвольные плагины.

## Следующие выпуски

**v0.2, при подтверждённой потребности:** parent proxy с HTTP или TLS-транспортом до родителя, отдельной авторизацией и правилами маршрутизации. Дополнительные методы входа по ключу рассматриваются по реальным требованиям клиентов: нестандартный секрет не делает обычный proxy совместимым с MTProto.

**v0.3, при подтверждённой потребности:** ограниченный shared HTTP cache с отдельным согласованием политики. Кэширование содержимого HTTPS внутри CONNECT без расшифровки невозможно; кэшируется только явно поддержанный HTTP-трафик.

## Нефункциональные требования

| ID | Требование | Способ проверки |
| --- | --- | --- |
| N01 | Отказ по умолчанию при отсутствии разрешающего правила | Отрицательные ACL-тесты; отсутствие исходящего соединения |
| N02 | Ограниченные соединения, очереди, буферы и фоновые работы | Проверка конфигурации, перегрузка и измерение ресурсов |
| N03 | Устойчивость к ошибочным запросам, обрывам и отмене | Негативные и fault injection тесты, fuzzing |
| N04 | Секреты не попадают в upstream и журналы | Контрольный origin и проверка логов с маркером секрета |
| N05 | Проверяемая сборка и происхождение зависимостей | Toolchain, Cargo.lock, CI, отчёт о зависимостях |
| N06 | Поддерживаемость другой моделью | Небольшие задания, явные контракты и регрессионные тесты |
| N07 | Предсказуемая работа на Linux | Установка, запуск, перезапуск, обновление и отказ запуска |

Не заявляются заранее превосходство над Squid и конкретная пропускная способность. Первые измерения фиксируют оборудование, версии, конфигурацию, число соединений, размер объектов и прогрев. Численные цели утверждаются по результатам базового стенда и требуемой нагрузки.

## Выбор стека

Предложение: Rust + Tokio + hyper + rustls. Причины: контроль памяти и владения ресурсами, асинхронный сетевой ввод-вывод, зрелые реализации HTTP/TLS, удобная сборка одного сервиса. Цена выбора — более сложное сопровождение асинхронных типов и потоковых тел; эту сложность ограничиваем одним crate и небольшими этапами.

Go — разумная альтернатива, если приоритетом окажутся скорость реализации и простота сопровождения командой. Язык утверждается до M01; точные версии совместимых библиотек и toolchain выбираются в M01 по актуальной официальной документации и фиксируются в репозитории.

## Решения, которые нужны от владельца

1. Подходит ли Rust или предпочтителен Go?
2. Основное применение: личный сервер, организация или сервис для многих внешних пользователей? Ожидаемое число активных клиентов и доступное железо?
3. Нужны ли кэширование и parent proxy уже в первом выпуске? Предложение — отложить их до готового базового сервиса.
4. Какие Linux-дистрибутивы и архитектуры обязательны? Предложение для начала — Ubuntu Server 24.04, x86_64, systemd; другие дистрибутивы не считаются автоматически поддержанными.
5. Достаточны ли вначале логин/пароль и ACL? Нужны ли сразу ключи, LDAP, ограничения скорости и трафиковые квоты?
6. Какая лицензия предполагается, если проект станет открытым? До решения LICENSE не добавляется.

Ответы изменяют документы, дорожную карту и задание M01. Приблизительная нагрузка или временно неизвестный размер сервера не мешают согласовать основные границы проекта; численные цели можно уточнить отдельно.
