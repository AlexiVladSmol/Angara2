### P2 (новое). Реестр `uri_epochs` держит неучтённую память

`StoreInner::uri_epochs` (`src/cache.rs:330`) — это `HashMap<String, u64>`. `bump_uri_epoch` (`src/cache.rs:619`) добавляет в него полный URI при каждом `invalidate` и `remove`, то есть после каждого успешного POST, PUT или DELETE. Записи не удаляются, когда наполнение завершилось. Если наполнения для этого URI не было, запись всё равно создаётся. Реестр очищается только при переполнении: 8192 URI. Request-target ограничен 8 КиБ (`MAX_REQUEST_TARGET_BYTES`), поэтому реестр может удерживать около 64 МиБ строк. В `cache_bytes` и `max_bytes` они не входят.

Стенд: один клиент, 8000 POST с разными URI около 8 КиБ, по одному соединению, все ответы 200.

| Кеш | Прирост RSS | `cache_bytes` |
| --- | --- | --- |
| Выключен | +0,5 МиБ | 0 |
| Включён | **+62,7 МиБ** | 0 |

Это та же проблема, что и P1: прирост RSS, которого не видно в `cache_bytes`. Длинные уникальные URI в POST — обычная картина для телеметрии и beacon-запросов с длинной query, так что реестр будет заполняться и при штатной работе. После очистки на 8192 URI аллокатор не обязательно вернёт память системе.

Ожидаемое исправление (одно из двух):
- **Хранить epoch только для URI с активным наполнением.** Запись создаётся в `begin_fill` со счётчиком ссылок и удаляется, когда наполнение завершается или сбрасывается. Тогда реестр ограничен `max_fills` (≤ 64), а `invalidate` и `remove` для URI без активного наполнения ничего в нём не создают.
- **Хранить вместо строки 64-битный хеш URI.** Коллизия даёт лишнюю отмену наполнения, это безопасно. 8192 записи — около 200 КиБ.

Проверка: тест, в котором тысячи POST с разными длинными URI не увеличивают RSS сверх небольшой константы. Можно взять за основу `m10_limits01`. Тест должен падать на `a228843`.
