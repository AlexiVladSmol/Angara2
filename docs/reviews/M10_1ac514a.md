### P1. Бюджет памяти не ограничивает реальный RSS

`CacheFill::push` хранит чанки тела через `data.clone()` (`src/cache.rs:780`), а заголовки — клоном `response.headers()` (`src/http/forward.rs:1412`). У hyper это срезы общего буфера чтения соединения с origin. Поэтому каждая запись держит весь буфер, в котором оказались её байты: до `max_buf_size`, то есть около 64 КиБ. В `cache_bytes` попадают только длины срезов.

Стенд, `max_bytes` 32 МиБ, объекты по 200 байт с `max-age=3600`:

| Сценарий | Записей | `cache_bytes` | Прирост RSS |
| --- | --- | --- | --- |
| Только маленькие объекты, кеш выключен | 0 | 0 | 0,3 МиБ |
| Только маленькие объекты, кеш включён | 512 | 0,43 МиБ | 5,4 МиБ |
| Перед каждым маленьким — ответ 1 МиБ `no-store` с того же origin, кеш выключен | 0 | 0 | 0,8 МиБ |
| То же, кеш включён | 512 | 0,43 МиБ | **38,8 МиБ** |
| То же, `max_entries = 2048` | 2048 | 1,71 МиБ | **153 МиБ** |

Это около 77 КиБ RSS на запись при учтённых ~880 байтах. Бюджет `max_bytes` до этих значений не доходит, и вытеснения нет (`cache_eviction = 0`).

Последствия:
- `max_entries` допускает до 65536 записей, то есть единицы гигабайт на ВМ с 1 ГБ;
- требование Issue про общий бюджет процесса и жёсткие пределы не выполнено;
- `cache_bytes` вводит администратора в заблуждение.

Ожидаемое исправление:
- копировать тело при наполнении в собственный буфер. Например, один `BytesMut` с точной ёмкостью, `freeze()` в `finish`; учитывать фактическую ёмкость;
- пересоздавать значения заголовков копией: `HeaderValue::from_bytes(value.as_bytes())`, а не `clone()`;
- проверка: воспроизводимый сценарий в репозитории (как существующие Linux RSS evidence в CI). Тысячи маленьких записей после крупных ответов по тому же соединению. Прирост RSS должен оставаться в пределах `cache_bytes` плюс небольшая константа. Сценарий должен падать на `1ac514a`.

### P2-1. Ревалидация: 304 с другим ETag даёт 502, многострочный `Cache-Control` теряется

**a) 304 с другим ETag.** `send_revalidation` (`src/http/forward.rs:1526`) побайтово сравнивает ETag из 304 с отправленным `If-None-Match`. При несовпадении клиент получает 502. Issue и описание PR требуют для непригодного 304 один безусловный GET в пределах deadline. Тест `m10_cache13` покрывает только случай `no-store`.

Стенд, оба ответа — 502, у origin по 2 запроса, повторного GET нет:
- запись `ETag: "v1"`, 304 с `ETag: W/"v1"`;
- запись `ETag: "v1"`, 304 с `ETag: "v2"`.

Слабая форма того же тега — обычное поведение, например nginx при сжатии. Здесь клиент получает ошибку на корректном ресурсе.

Ожидаемое исправление:
- несовпадение ETag обрабатывать как непригодный 304: удалить запись и сделать один безусловный GET;
- для сопоставления использовать слабое сравнение (RFC 9110 §8.8.3.2);
- тесты на оба случая.

**b) Многострочный `Cache-Control` в 304.** `updated_meta` (`src/cache.rs:949`) берёт `headers.get(name)`, то есть только первую строку поля, и `insert` заменяет им все сохранённые строки. Стенд: 304 со строками `Cache-Control: max-age=60` и `Cache-Control: no-store`. Третий GET отдан из кеша, у origin по-прежнему 2 запроса. `no-store` из второй строки потерян, запись живёт ещё 60 с.

Ожидаемое исправление:
- переносить все значения поля: удалить старые, затем `append` каждой строки;
- тест с `no-store` во второй строке.

### P3

**P3-1. Глобальный epoch.** Любые `invalidate`, `remove` или смена Vary увеличивают один общий счётчик (`src/cache.rs:375/471/660`). Это отменяет публикацию всех идущих наполнений, а не только того же URI. Стенд: медленное наполнение (512 КиБ за ~3 с) и POST на другой origin посреди него. Объект не сохранился, повторный GET снова ушёл на origin; без POST — попадание. В офисе POST идут постоянно, поэтому крупные объекты будут сохраняться редко. Issue допускает более широкую очистку только при неопределённости. Предложение: epoch на URI (карта URI → счётчик) или проверка при публикации по множеству инвалидированных URI.

**P3-2. `cache_bytes` после 304.** `revalidate` заменяет заголовки записи, но не меняет учёт, хотя новые заголовки могут быть длиннее.
