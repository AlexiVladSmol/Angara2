Ревьюер — Claude Opus 5.5. Решение о слиянии принимает владелец.

Схема процессов сделана правильно. Прокси не получает права записи, writer принимает только типизированные операции, право записи проверяется по peer UID на стороне сервиса. Запись файлов атомарная, со сверкой версии, а применение подтверждается сверкой поколения и версии после reload. Блокировка проверяется при каждой аутентификации, кеша учётных данных нет. Блокируют слияние два P2: привилегированный writer ни разу не запускался как установленный systemd unit, и добавить первого пользователя в пустой users-файл нельзя.

### Что сделано хорошо

- **Права.** Приватный `control-read.sock` (0600) доверяет reload только root и своему UID, мутирующие операции на нём закрыты. Публичный сокет 0660 `root:angara`; `is_admin` пускает root и членов `angara-admin`. Тестовый обход `test_allow_uid` доступен только из тестов, флага CLI или переменной для него нет. `config.apply` не принимает текст конфигурации, а применяет файл с диска; `access.apply` меняет только `access`, поэтому через API нельзя перенаправить `users_file` на другой файл.
- **Применение.** `applied` выставляется, только если после reload поколение совпало и активная версия users/config равна сохранённой. Иначе состояние `unknown` или `saved` с причиной. Это ровно то, что требует таблица в разделе 4 Issue.
- **Блокировки.** `active_user` проверяет блокировку по `Clock` при каждой аутентификации. Заблокированный пользователь проходит путь с dummy-хешем и получает 407. Время ответа при этом такое же, как для обычного отказа. Граница `now >= until` соответствует Issue.
- **Секреты.** Пароль передаётся как `Zeroizing`, строка запроса на сервере затирается, writer ничего не пишет в журнал, в протоколе нет PHC.

### P2-1. Установленный writer не проверен ни в CI, ни на стенде

В CI нет ни одного шага, который запускает `angara-control.service`: `angara-control`, `control.sock` и `control-write` встречаются только в unit-тестах с временными сокетами. `systemd-analyze verify` проверяет синтаксис, но не поведение. Для unit с `PrivateNetwork`, `RestrictAddressFamilies=AF_UNIX`, `MemoryDenyWriteExecute`, `ProtectSystem=strict` и узким набором capabilities этого мало. Раздел 3 Issue прямо требует проверить разрешённый и запрещённый вызов в установленном unit, а в отчёте A10 сказано «на стенде» — это не выполнено.

Отдельный риск с каталогом `/run/angara`. Он создаётся через `RuntimeDirectory=angara` в **`angara.service`**, а в нём лежит сокет **writer-а**. При `RuntimeDirectoryPreserve=no` (по умолчанию) systemd удаляет каталог при каждой остановке прокси, в том числе при аварийном перезапуске. Явный `systemctl restart angara` распространяется на writer через `PartOf=` и, скорее всего, безопасен. Аварийный перезапуск после `kill -9` — не обязательно: writer может остаться работать без файла своего сокета, и `angara tui` получит «нет такого файла». Кроме того, у writer `/run/angara` подмонтирован через `ReadWritePaths=`. Как поведёт себя это монтирование после удаления и пересоздания каталога, надо проверить на практике.

Что нужно:

1. Добавить в job `systemd` (или в отдельный job) шаги на установленном архиве:
   - пользователь только из группы `angara` выполняет `hello`/`snapshot` (успех) и `user.add` (`unauthorized`);
   - член `angara-admin` (или root) выполняет `user.add` и `block.set`, после чего реальный запрос получает 407;
   - после `kill -9` основного PID прокси и его автоматического перезапуска `control.sock` существует, а запись снова проходит.
2. Если третий шаг не проходит, сохранять каталог при перезапуске: например, `RuntimeDirectoryPreserve=restart` в `angara.service` или отдельный runtime-каталог у writer-а, к которому группа `angara` имеет доступ. Выбор оставляю исполнителю.

### P2-2. Первого пользователя нельзя добавить в пустой users-файл

`apply_users_edit` начинается с `document["users"].as_array_of_tables_mut()`. Для файла вида

```toml
version = 1
users = []
```

это inline-массив, а не `[[users]]`, поэтому `user.add` отвечает `users must be an array of tables`. Такой файл проходит штатный валидатор: в `auth.rs` есть тест `UsersSnapshot::parse("version = 1\nusers = []\n")`. Это естественная отправная точка, когда пользователей заводят через TUI. Тест `adding_a_duplicate_or_missing_user_is_rejected` начинает с непустого `USERS`, поэтому случай не покрыт.

Исправление: если `users` — пустой inline-массив, заменить его на пустой `ArrayOfTables`. Непустой inline-массив можно по-прежнему отклонять с понятным сообщением. Нужен unit-тест на пустой файл и строка в A02.

### P3 (не блокируют)

- **Откат на M10 при users v2.** Если в файле есть `blocked_until`, бинарник M10 не стартует. В 11.3 это сказано, но в разделе об откате (`angaractl rollback`) и в `RELEASE_CHECKLIST.md` — нет. Администратор, откатывающий выпуск, прочитает именно этот раздел. Достаточно одной фразы там же: перед откатом снимите временные блокировки или восстановите users-файл.
- **`is_admin` читает `/etc/group` и `/etc/passwd` напрямую.** Группы из NSS (LDAP, sssd) writer не увидит, и такой администратор получит `unauthorized`. Для локального стенда это нормально, но стоит одной строкой записать в ADMIN_GUIDE, что `angara-admin` должна быть локальной группой.
- **Копии пароля в TUI-клиенте.** `client.rs` кладёт пароль в `serde_json::Value` (`json!({"password": password.as_str(), …})`), а затем в строку `serde_json::to_string`. Ни то ни другое не затирается, хотя сервер свою копию затирает. Это гигиена памяти клиентского процесса, а не утечка наружу. Если делать, то собирать строку запроса в `Zeroizing<String>`.
- **Writer не стартует при невалидном конфиге.** `run_control_write` вызывает `Config::load` до запуска. Если на диске невалидный TOML, writer упадёт, после трёх попыток unit станет `failed`, и экран «Конфигурация» не покажет причину. Ожидаемо ли это, решать исполнителю. Если да — одна строка в разделе неисправностей ADMIN_GUIDE.
- **A07 без CONNECT.** Issue требует проверить first-match реальным HTTP/CONNECT; тест `m11_acl02` проверяет только HTTP. Это ограничение уже указано в PR, просто фиксирую.
