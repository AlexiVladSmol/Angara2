### P2. Отмена push-прогона в `main` теряет проверку кода

В workflow с `main` уже есть:

```yaml
concurrency:
  group: ci-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true
```

Для push в `main` группа одна — `refs/heads/main`. Если два слияния идут подряд, второй push отменяет прогон первого. Так и было сегодня: слияния #9 и #10 разделяли 10 секунд, push-прогон [45991765521](https://github.com/AlexiVladSmol/Angara2/actions/runs/45991765521) для `ee37a91` завершился со статусом `cancelled`.

До этого PR это не мешало: следующий push всё равно запускал полный набор на дереве, где есть оба изменения. Теперь следующий push выбирает режим по своему диапазону `before..after`. Если второе слияние — только документы, получится:

1. слит код (`A`), его push-прогон запущен;
2. через несколько секунд слит README (`B`), прогон `A` отменён;
3. прогон `B` выбирает лёгкий режим и зеленеет.

В итоге `main` зелёный, а код из `A` в `main` штатным CI не проверялся ни разу. Issue требует, чтобы при ошибке итог не мог стать зелёным из-за пропущенных jobs. Отмена прогона — та же ошибка, просто на соседнем коммите.

`cancel-in-progress: false` не решает задачу полностью: GitHub держит в группе только один ожидающий прогон, и третий push всё равно отменит второй. Ожидаемое исправление — у каждого push свой прогон в своей группе:

```yaml
concurrency:
  group: ci-${{ github.workflow }}-${{ github.event_name == 'push' && github.sha || github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}
```

Для PR отмена остаётся безопасной: селектор PR берёт весь diff от merge-base, поэтому последний прогон покрывает все коммиты. Попутно push в `main` больше не отменяет ручной dispatch с soak на `main` — сейчас это тоже возможно.

Отдельно стоит одной фразой записать в D66 или WORKFLOW: лёгкий push-прогон проверяет только свой диапазон и не подтверждает исправность `main`. Если предыдущий push-прогон красный, зелёный лёгкий прогон поверх него ничего не исправляет.

### Красный PR-прогон — не из-за PR

`m10_cache48_many_idle_invalidations_do_not_cancel_slow_fill` нестабилен. Это не регрессия PR, и это мой пропуск в ревью PR #9.

- Origin держит хвост медленного тела до `Notify` из теста, поэтому медленный клиент ничего не получает, пока идут 8300 POST.
- Медленный запрос читает через `RawClient`, у которого на каждое чтение таймаут `IO_TIMEOUT` = 5 с (`tests/common/m03.rs:18`, `:318`).
- Если 8300 POST на загруженном раннере идут дольше 5 с, чтение медленного запроса падает (`tests/m10_cache.rs:37`, `read response`). Задача завершается, и проверка `!slow.is_finished()` на строке 1974 срабатывает.

В ревью PR #9 я написал, что тест «больше не зависит от скорости 8300 POST». Это неверно: зависимость осталась через 5-секундный таймаут клиента. Исправление для отдельного Issue: пока origin ждёт `Notify`, он раз в секунду отдаёт по байту тела, сохраняя общую длину 4096. Либо медленный запрос читает собственным клиентом с таймаутом больше длительности серии POST.

Для этого PR новый коммит с правкой P2 сам запустит PR-прогон. Если `m10_cache48` упадёт снова, решение о повторе — за владельцем, как сказано в AGENTS.

### P3 (не блокируют)

- **Селектор оценивает сам себя.** `scope` запускает `ci/doc_changes.py` из head PR, а его тесты выполняются только в режиме `full`. Если правка селектора ошибочно отнесёт `ci/` или `.github/` к документам, этот PR получит лёгкий режим, тесты селектора не запустятся, итог будет зелёным. От злого умысла это не защищает: workflow PR и так берётся из head. Но от случайной ошибки защитит запуск селектора из базовой ревизии: `git show "$BASE:ci/doc_changes.py"`, а если файла в базе нет — `full`.
- **`PACKAGED_DOCS` задан вручную.** Сейчас он совпадает с `build-release.sh`. Если упаковщик начнёт копировать новый документ, список отстанет молча. Достаточно unit-теста в режиме `full`, который сверяет список с `.md` из `install`-строк `build-release.sh`.
- **Исполнитель.** В Issue #14 исполнитель — DeepSeek, в PR — «ChatGPT по прямому поручению владельца». Подтверждение — за владельцем.

### Итог

CHANGES_REQUESTED на `3ae42ee`, причина — только P2. Нужны правка `concurrency` (и желательно фраза в D66 или WORKFLOW) и зелёный PR-прогон на новом head. Dispatch не нужен: `src/` и `packaging/` не меняются. После этого одобрю.
