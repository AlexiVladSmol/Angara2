## Состав работ, если утверждён Rust

1. Один crate с lib и bin. Создать только необходимые текущему этапу модули CLI/config/runtime; остальные границы описать в документации.
2. Выбрать стабильный совместимый Rust toolchain, закрепить его, добавить Cargo.lock. Обосновать прямые зависимости и не добавлять неиспользуемые networking библиотеки заранее.
3. Реализовать --version, check --config и serve --config. До M03 serve завершается понятным сообщением о недоступности proxy и ненулевым кодом; успешная имитация рабочего сервера недопустима.
4. Спроектировать и описать версионируемую TOML-схему. В этом этапе реально валидировать listener address, конфликты, timeout/limit ranges и неизвестные поля. Будущие параметры не должны молча приниматься, будто реализованы.
5. Добавить безопасный пример и ошибки config без вывода секретов. check не открывает listener, не выполняет DNS и не соединяется с origin.
6. Настроить CI для format/lint/locked build/tests. Выбрать поддерживаемый способ dependency checks и согласовать политику исключений/лицензий.
7. Добавить точные инструкции локальной сборки, запуска проверок и фактический CI report.

При выборе Go Codex перепишет это задание до выдачи исполнителю.

## Критерии приёмки

- Чистая копия репозитория собирается по инструкции на согласованной ОС; версии записаны.
- --version возвращает версию и успешный код.
- check принимает минимальный валидный пример и возвращает успешный код.
- Отсутствующий файл, повреждённый TOML, неизвестный ключ, нулевой/отрицательный либо чрезмерный limit и дублирующий listener дают ненулевой код и понятную ошибку.
- check не имеет сетевых побочных эффектов; это подтверждено тестом через наблюдаемую границу/инъекцию, а не только комментарием.
- Ошибки и тестовые логи не содержат маркер секретного поля. Если schema пока не имеет секретов, тестирует применимую диагностическую границу без выдуманного auth backend.
- CI проходит на head SHA; непрошедшие и недоступные проверки указаны.
- В PR нет сетевого forwarding, cache, auth implementation и изменения утверждённой архитектуры.

## Обязательные проверки

CFG-01 и CFG-02 из docs/TEST_STRATEGY.md в объёме реализованной конфигурации; отдельно проверить границы duration/usize и конфликты настроек. CLI-тест запускает настоящий бинарник и проверяет exit status/stdout/stderr. Не создавать тесты, которые просто повторяют вызов той же validation function как ожидаемый результат.
