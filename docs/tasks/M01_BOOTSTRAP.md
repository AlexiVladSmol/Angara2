# Задание DeepSeek: M01 — Rust, конфигурация и многопоточный runtime

**Статус: READY.** M00 согласован владельцем 9 ноября 2026 года; ревизия документов 0.2. Код, тесты и CI выполняет DeepSeek V4.1 Flash 1017; Codex проектирует и проводит ревью.

## 1. Цель и исходная база

Создать минимальную поддерживаемую основу Angara: воспроизводимая сборка Rust на Ubuntu Server 24.04 x86_64, CLI, проверяемый TOML и многопоточный Tokio runtime. На этом этапе рабочего сетевого proxy ещё нет.

Авторитетный SHA документации и ссылка на задание закрепляются в отдельном Ready Issue M01. Прочитать AGENTS.md, docs/DECISIONS.md, PROJECT_BRIEF, ARCHITECTURE и TEST_STRATEGY на этом SHA. До слияния PR M00 начать ветку от закреплённого коммита docs/m00-proposal и направить PR туда. Если документы уже слиты, использовать main с ними и указать фактический base SHA. Согласование M00 не разрешает самостоятельное слияние.

В начале работы оставить в Issue короткий план. Следовать согласованным ролям: Codex не пишет реализацию вместо DeepSeek.

## 2. Состав работ

1. Один crate с lib и bin angara. Модули cli/config/runtime; остальные компоненты пока описаны документацией.
2. Выбрать совместимый стабильный Rust toolchain, закрепить rust-toolchain.toml и Cargo.lock. Tokio нужен уже для runtime. hyper/rustls подключать при появлении использующего их кода, не ради списка зависимостей. Прямые зависимости и выбранные возможности обосновать.
3. Реализовать angara --version, angara check --config <path> и angara serve --config <path>. До M03 serve валидирует config и заканчивается сообщением «proxy ещё не реализован» с ненулевым кодом; listeners и upstream не открываются. Runtime отдельно реально создаётся и проверяется тестом, без успешной имитации работающего proxy.
4. Ввести schema_version и строгую TOML-схему. Минимум: runtime.worker_threads = "auto" либо положительное целое; массив listeners со стабильными уникальными id, числовым IP:port и поддержанным transport; необходимые ограниченные timeouts/limits. Поддержанный transport в M01 — http. TLS, auth, egress rules, cache и admin API пока не реализованы: соответствующие активные настройки отклоняются, а не молча игнорируются.
5. Реально валидировать хотя бы два listener definitions, дубли id, одинаковые адреса, перекрытие wildcard с конкретным адресом того же семейства/порта. Для M01 IPv6 listener проектировать как IPv6-only; конфликт IPv4/IPv6 и политику будущего socket bind описать, чтобы serve в M03 мог исполнить тот же контракт. Не выполнять пробный bind ради check.
6. Для auto использовать доступный процессу параллелизм с безопасным минимумом один; явное число задаёт многопоточный runtime. Зафиксировать разумную верхнюю границу workers и численных limits с обоснованием. Ноль, отрицательные значения, переполнение и превышение границы — ошибка. worker_threads не определяет максимум клиентов; 10–20 устройств могут создавать много соединений.
7. Подготовить построение и контролируемое завершение Tokio multi-thread runtime. В тесте подтвердить заданное число workers через доступный публичный API runtime и выполнение асинхронных задач; проверить вариант с одним worker и auto. Не писать искусственный benchmark и не обещать ускорение по тесту настроек.
8. Привести безопасный минимальный config и отдельный валидный пример нескольких listeners, команды сборки/проверки и ясные ошибки с ненулевым exit code. check не выполняет DNS, не принимает подключения и не соединяется с origin. Ошибки не дампят целиком config и пользовательский ввод.
9. Настроить CI: format, lint, locked build, unit/integration/CLI проверки на Ubuntu 24.04. CI jobs имеют минимальные read permissions без production secrets; внешние actions закреплены SHA. Конкретные команды, версии и runner записать в README.
10. Выбрать dependency advisory/license tooling и явно описать политику. Лицензия самого Angara отложена; не выбирать её и не создавать LICENSE от имени владельца. Проверять зависимости можно без принятия лицензии проекта. Не создавать молчаливые исключения, чтобы сделать CI зелёным.

## 3. Границы

Входят CLI, config, runtime, примеры, CI, инструкции и необходимые тесты. Не входят HTTP forwarding, CONNECT, auth implementation, ACL engine, настоящий DNS/dial, управление маршрутами Linux, parent, cache, TUI и web server.

Схема listeners и границы модулей должны допускать дальнейшие несколько интерфейсов. Полные egress-профили и порядок route rules уточняются в M02, реальный сетевой bind — M02/M03. В M01 не создавать пустые реализации будущих backend и не принимать неработающие параметры как поддержанные.

Согласованный стек и архитектура остаются Rust/Tokio/hyper/rustls. Новые зависимости с существенным влиянием, unsafe и собственный HTTP parser не добавлять без архитектурного решения.

## 4. Критерии приёмки

- Чистая копия собирается по README на Ubuntu 24.04 x86_64 закреплённым toolchain с Cargo.lock.
- --version возвращает корректную версию и нулевой код.
- check принимает минимальный config и пример нескольких listeners, возвращая нулевой код без сетевых операций.
- Повреждённый TOML, неизвестный schema_version/ключ, отсутствующий файл, неизвестный transport, неверные IP/port, дубли id/адресов и документированные wildcard-конфликты отвергаются.
- Worker auto и явное число распознаны; крайние значения workers/timeouts/limits, переполнение и неподдержанные будущие поля отвергаются.
- Runtime действительно многопоточный, имеет заданное число workers, исполняет задачи и завершается без оставшихся задач/потоков. Отчёт отделяет этот контракт от будущего измерения производительности.
- check не открывает сеть; отдельная проверка доказывает отсутствие listener, resolver и dial операций через наблюдаемую границу либо инструментацию процесса. Один запрос на свободный порт не считается достаточным доказательством.
- serve пока не слушает сеть и возвращает документированный ненулевой код недоступности proxy; тест запускает настоящий бинарник.
- Маркер чувствительного значения из ошибочного config не появляется в stdout/stderr/CI artifacts; сообщения сохраняют полезное имя поля/позицию. Не требуется выдумывать auth backend ради теста.
- CI проходит на конкретном head SHA. Непрошедшие или недоступные проверки указаны явно; отсутствие доступа к runner не записано как успех.
- PR содержит только M01 и инструкции; остаётся прозрачным, что работающего proxy ещё нет.

## 5. Проверки и отчёт

Обязательные сценарии: CFG-01/02/03 в применимом объёме и CPU-01 в части runtime. CLI-тесты запускают настоящий бинарник и проверяют exit status/stdout/stderr. Тесты используют временные файлы и cleanup; assertions выводятся из контрактов, не повторяют тот же validator как ожидаемый результат.

Обычные команды Rust: cargo fmt --check, cargo clippy --locked --all-targets -- -D warnings, cargo build --locked, cargo test --locked. Если используются features/workspace, конкретный эквивалент фиксируется в README и CI. Привести фактически выполненные команды, версии, ОС, passed/failed/skipped, ссылки на CI и head SHA; результаты не заполнять заранее.

В PR указать Issue, base/head SHA, причины выбора зависимостей и численных границ, матрицу критериев, ограничения и следующий шаг. После принятия M01 Codex готовит M02 с точной моделью ACL, egress/routing и контрактами resolver/transport; DeepSeek не расширяет задание самостоятельно.
