## 2. Сборка и состав поставки

1. Собрать `x86_64-unknown-linux-gnu` на Ubuntu 24.04 через `cargo build --locked --release` с закреплённым в репозитории toolchain. Записать версии rustc/Cargo, архитектуру ELF и зависимости для запуска. Проверить архив на отдельной целевой системе. В среде установки команды Cargo не вызываются.
2. Выпускать архив вида `angara-0.1.0-linux-x86_64-<short-sha>.tar.gz`, внешний `SHA256SUMS` и ссылку на соответствующую сборку CI. Включить бинарник, unit, установщик и команды обслуживания, безопасные примеры, инструкцию, манифест и уведомления о лицензиях зависимостей.
3. В `manifest.json` указать версию формата и пакета, полный SHA исходников, target, профиль, версии инструментов, SHA-256 для Cargo.lock и установленного бинарника, список файлов. Архив целиком сверяется с **внешней** контрольной суммой, полученной из доверенной сборки. Сохранять состав и порядок упаковки воспроизводимыми. Побитовое совпадение независимых сборок заявлять только после измерения.
4. Зафиксировать набор реально использованных зависимостей, их версии, лицензии и необходимые LICENSE/NOTICE. Включить описание локального изменения `vendor/hyper-1.12.0/ANGARA_PATCH.md`. В архиве и публичных отчётах исключить конфигурацию оператора, записи пользователей, PHC, пароли, приватные ключи, токены и резервные копии. Лицензия самой Angara остаётся открытым решением.

## 3. Установка и безопасная исходная конфигурация

| Объект | Раскладка для кандидата |
| --- | --- |
| Бинарник версии | `/opt/angara/releases/<candidate-id>/bin/angara`, владелец `root:root`, режим `0755` |
| Активная версия и CLI | Ссылка `/opt/angara/current` под контролем root. Команда `/usr/local/bin/angara` указывает на активный бинарник |
| Unit | `/etc/systemd/system/angara.service`, управляется root. Сервису доступно только чтение |
| Настройки | Каталог `/etc/angara` с правами `root:angara 0750`. Основной файл `angara.toml` с правами `root:angara 0640` |
| Users-файл и приватный TLS-ключ | `root:angara 0640`. Группа содержит только доверенную служебную учётную запись |
| Цепочка сертификатов | `root:root 0644` либо `root:angara 0640` |

Установщик создаёт системного пользователя и группу `angara` без интерактивного входа и дополнительных привилегий. Проверить владельца, режим и чтение файлов с эффективным UID сервиса. При конфликте с уже существующей чужой учётной записью или неуправляемым путём завершать операцию с диагностикой. При повторной установке сохранять рабочие настройки, users-файл, ключи и локальные systemd drop-in.

Предусмотреть непривилегированный режим `DESTDIR` для проверки дерева файлов. Все изменения в этом режиме ограничены staging-каталогом. Запуск `useradd`, `systemctl` и запись в системные пути хоста допускаются только при реальной установке или обслуживании. До выполнения поставленного кода проверить внешний SHA-256. Распаковка и установка отклоняют обход каталогов, небезопасные ссылки и запись через доступный посторонним каталог. Собственный процесс не получает прав изменять бинарник, unit или конфигурацию.

Начальная установка оставляет запуск и включение автозапуска явными действиями администратора. Исходная конфигурация слушает только loopback на непривилегированном порту. Локальному тестовому клиенту разрешён вход для проверки, запросам к назначениям доступ закрыт. Контрольный запрос получает HTTP 403, а контролируемый origin подтверждает отсутствие подключения. Включение Basic/TLS, добавление пользователей и разрешающего ACL выполняются по инструкции. Шаблоны не содержат заводских паролей и не включают небезопасный Basic на внешнем адресе.

## 4. Контракт systemd

- **Запуск.** Один foreground-процесс с `Type=exec`, `User=angara` и `Group=angara`. В `ExecStartPre` вызвать `angara check --config /etc/angara/angara.toml`, в `ExecStart` — `angara serve --config /etc/angara/angara.toml`. Использовать абсолютные пути к одной активной версии. Готовность подтвердить запросом через прокси с ожидаемым ответом за установленный срок. Зафиксировать PID, UID, группы, capabilities и фактические слушающие сокеты.
- **Reload.** `ExecReload` отправляет SIGHUP основному PID. Успешный возврат `systemctl reload` подтверждает отправку сигнала. В тесте привязать чтение журнала к курсору перед действием, дождаться `reload_applied` или `reload_rejected` и проверить доступ **следующим запросом**, в том числе по уже открытому keep-alive. Для неверного файла или изменения, требующего перезапуска, сохраняются действующие ACL и PID. Отдельно проверить серию сигналов. Новый управляющий порт для этого не нужен.
- **Остановка.** Штатный SIGTERM, `KillMode=control-group` и `TimeoutStopSec=315s`. Конфигурация Angara допускает до 300 000 мс на завершение. Unit оставляет процессу этот срок с запасом. Для обычного профиля задать 5 000 мс. Проверить штатное завершение и принудительное закрытие соединений самим приложением при малом таймауте. В обоих сценариях systemd не посылает SIGKILL, порты освобождаются, процессов в cgroup не остаётся.
- **Восстановление.** Исходный профиль — `Restart=on-failure`, `RestartSec=2s`, `StartLimitIntervalSec=60s`, `StartLimitBurst=3`. Проверить намеренный stop, аварийное завершение, ошибку конфигурации и занятый порт. После исчерпания лимита инструкция позволяет устранить причину и запустить сервис снова.
- **Изоляция.** Применить `NoNewPrivileges=true`, пустые `CapabilityBoundingSet=` и `AmbientCapabilities=`, `UMask=0077`, `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`, `PrivateDevices=true`, `ProtectKernelTunables=true`, `ProtectKernelModules=true`, `ProtectControlGroups=true`, `RestrictSUIDSGID=true`. Проверить работу DNS/NSS, IPv4/IPv6, TLS, выбора исходящего IP и чтение необходимого процессу `/proc/self/status`. Исходные `LimitNOFILE=16384` и `TasksMax=512` относятся к профилю пилота. Показать фактические лимиты и запас для выбранной нагрузки.
- **Журнал.** Направить вывод в journald. Записи `serve` сохраняют JSON Lines и правила конфиденциальности M07. Сообщения manager и `check` учитываются отдельно при разборе. Проверить отсутствие заранее подготовленных маркеров секретов в журнале, диагностике и запросе, полученном origin. Проверять прикладной счётчик потерь журнала при перегрузке существующими средствами.

## 5. Обновление и откат

Реализовать операции установки новой версии и возврата предыдущей. До остановки работающего A проверить архив B, развернуть B в отдельном каталоге и вызвать **бинарник B** с рабочей конфигурацией от пользователя `angara`. После явной команды оператора остановить A, атомарно переключить `current` переименованием на том же файловом разделе, запустить B и выполнить проверочный запрос. Сохранять согласованность бинарника, unit и служебных скриптов при переходе в обе стороны. При изменении unit выполнить `daemon-reload`.

Для испытания собрать A из закреплённого M07, B из проверяемого коммита M08. Допустимо упаковать A сборщиком из M08 с отдельной записью SHA упаковщика и SHA исходников A. Проверить A→B→A по манифесту, `/proc/<pid>/exe`, результату проксирования и хешам локальных настроек. Если бинарники совпали побайтово, показать фактически активированные каталоги обеих версий.

Повреждённый архив, ошибка контрольной суммы или непрочитанный users-файл/ключ должны обнаруживаться до переключения. Работающий A сохраняет PID и обслуживает запросы. При отказе старта после переключения вывести причину и дать рабочую команду отката. Проверить фактическое восстановление после освобождения занятого порта. При прерывании между остановкой и запуском повтор команды либо явный откат приводит к целой выбранной версии.

Обновление сохраняет настройки, TLS-материалы и локальные изменения администратора. Резервная копия совместимой конфигурации хранится в приватном каталоге root. Откат бинарника не восстанавливает пароль или ACL автоматически. В runbook отдельно показать явный откат согласованного набора файлов и проверку доступа. Активная и предыдущая версии доступны до решения оператора об очистке.

## 6. Стенд, сеть и нагрузка

Обязателен как минимум один прогон на Ubuntu 24.04 x86_64 с настоящим systemd в роли PID 1, cgroup и правами для создания тестовых интерфейсов. Подходит одноразовая VM или изолированный runner. Устанавливается тот архив, который отдала сборка. Зафиксировать его SHA-256. На принимающей стороне тест обходится без исходников и инструментов Rust. Проверку `systemd-analyze verify` дополнить фактическими start, reload, stop, restart, upgrade и rollback. Для заявленной инструкции `enable` проверить запуск после загрузки одноразовой VM. Команды, меняющие службу и сеть, выполняются на стенде.

**Функциональный прогон.** Проверить отдельные HTTP- и HTTPS-listeners, правильные и неверные credentials, ответы 407 и 403, допустимый HTTP-запрос, CONNECT к контролируемому сайту и отсутствие исходящего соединения при отказе ACL. Для TLS до прокси и TLS до сайта использовать две независимые тестовые CA. Проверить успешный путь, неверную CA и неверное имя. В положительных примерах проверка сертификата включена. Создавать временные секреты только на стенде.

**Несколько интерфейсов.** Настроить два разных veth-интерфейса или NIC с отдельными адресами и маршрутами к контролируемым origins. Проверить вход на обеих точках, выбор исходящего профиля по пользователю или listener, адрес источника у origin и счётчики соответствующего интерфейса. Убрать выбранный тестовый адрес, выполнить новое исходящее соединение и подтвердить явный отказ без перехода на другой интерфейс. По окончании удалить только созданные стендом ресурсы. Указать, какие интерфейсы были виртуальными или физическими.

**Несколько ядер.** Сохранить доступные процессу CPU, cpuset и квоту. Сравнить одинаковый профиль на 1 и 2 workers, добавить 4 при наличии ресурса. Проверить работу на нескольких доступных ядрах по активности рабочих потоков. Показать CPU по потокам, пропускную способность и задержки. Четыре потока на двух vCPU учитывать как отдельную конфигурацию.

| Профиль | Условия и измеряемый результат |
| --- | --- |
| Короткий пилот | 10, затем 20 независимых клиентов, не менее 60 секунд на когорту после прогрева. Две тестовые учётные записи, обычные HTTP-запросы, загрузка в обе стороны, HEAD/Range, HTTPS до прокси и CONNECT. Каждый клиент выполняет полезную работу |
| Длительный прогон | 2 минуты прогрева и 60 минут измерения на 20 клиентах. Включены TLS и Basic, смешаны HTTP и CONNECT. Во время работы применить допустимый reload и отвергнуть неверное изменение. Отдельный контрольный запрос продолжает успешно проходить по действующим правилам |
| Перегрузка и сбои | Параллельные проверки Basic, лишние соединения и TLS-handshakes, медленные клиенты, ошибки DNS/подключения, разрыв соединения, stop под нагрузкой. Заранее записать ожидаемые исходы при исчерпании лимитов |
| Потоковая передача | 64 МиБ и не менее 1 ГиБ через HTTP и CONNECT при одном и том же числе соединений. Сверить размер и хеш полученных данных. Ограничить буферы клиента и origin, проверить освобождение ресурсов после обрыва |

Стенд работает с локальными данными, фиксированным seed, числом клиентов, темпом запросов, количеством соединений на клиента и конфигурацией. Физические устройства и их эмуляция указываются раздельно. Логический клиент может открывать несколько соединений. Выбрать темп с учётом цены Argon2. Задокументировать любые изменения лимита проверок паролей в нагрузочном профиле. В штатном пилоте ожидаются полный обмен у каждого клиента и отсутствие неожиданных ошибок. Преднамеренные 403, 407, 503, таймауты и сбросы учитывать по сценариям. В отчёт попадают все попытки и повторы.

Для одного и того же профиля стенда зафиксированы начальные контрольные пороги процесса Angara. Пиковый RSS — до 512 МиБ. После закрытия клиентов, завершения фоновых работ и истечения idle TTL пула с запасом 5 с допустимы до 8 FD и до 64 МиБ RSS сверх прогретой базы. Снять ряд измерений во время часового прогона. Потребление памяти и FD должно оставаться ограниченным при увеличении размера объектов и числа reload. Эти числа выбраны для регрессии на стенде. Производственные цели по пропускной способности и задержке определяются после пилота. Отклонение описать с измерениями до изменения критериев.

Отчёт включает ОС, ядро, RAM, CPU/квоты, workers, версии systemd и curl, конфигурацию, число устройств/клиентов, соединений, запросов и туннелей. Привести число ошибок каждого типа, количество измерений, throughput, задержку p50/p95/max и значения RSS/FD/потоков до, на пике и после нагрузки. Число потоков ОС измерять через `/proc/<pid>/task`. Сведения об async-задачах брать из существующих регрессий, явно указывая границы наблюдения.

## 7. CI и комплект сдачи

Сохранить действующие fmt, Clippy с `-D warnings`, locked build/test, cargo-deny и отдельные ресурсные прогоны. Включить сборку release, проверку скриптов/юнита, передачу архива и испытание в отдельной среде исполнения. В частности, сохранить регрессии границ HTTP/CONNECT, 20 последовательных повторов M04 forced-shutdown, проверки Argon2/TTY, TLS-in-TLS, бюджетов и поколений M07. Для N03 использовать ограниченный по времени и размеру входа набор воспроизводимых ошибочных запросов/конфигураций и мутаций. Проверять отсутствие зависаний, panic и соединений с origin при запрещённых запросах. Можно повторно использовать существующие тесты и сценарии.

Короткие проверки идут в обычный CI. Часовой сценарий реализовать как одну команду стенда с ограничением общего времени, например 90 минут. До ревью выполнить её на точном SHA кандидата с тем же SHA-256 архива. Подходит запуск на одноразовой Ubuntu VM с сохранённым отчётом или отдельный CI job, доступный из ветки PR. Новый `workflow_dispatch` может служить ручной точкой входа после появления workflow в основной ветке. Ссылку на результат и хеш архива прикладывать к PR или CI run после сборки, чтобы запись отчёта не требовала менять проверенный коммит. Привилегированные проверки выполняются на изолированном стенде, без рабочих секретов и write-токена. GitHub Actions закреплять полными SHA.

Подготовить инструкцию администратора с командами установки, проверки поставки и контрольного запроса, включения TLS/Basic/ACL, безопасного ввода через `angara users hash`, проверки конфигурации от служебного UID, чтения журнала, reload/остановки, обновления, отката и удаления. При удалении сохранить конфигурацию и данные оператора по умолчанию. Привести типичные неисправности и диагностику занятого порта, прав, неверного сертификата и лимита FD. Для автоматической проверки пароля использовать явный `--password-stdin` с синтетическим секретом. Для оператора пароль не попадает в argv, окружение или историю shell.

Приложить checklist выпуска и матрицу **F01–F11, N01–N09 → проверка → доказательство → ограничение**. Удобные доказательства — ссылка на job или санитизированный отчёт, команда, SHA исходников и архива, измеренный результат. Указать попытки, завершившиеся ошибкой, и причины повторного запуска. Сценарий без доступного systemd, IPv6, двух интерфейсов или достаточного числа CPU переносится на подходящий стенд. Результат ручного пилота владельца и решение о публикации остаются открыты до их фактического выполнения.
