# Angara — этапы разработки

Статус: **M00 согласован, M01 READY; ревизия 0.2 от 9 ноября 2026 года**. Сроки не назначены. Каждый этап разбивается на небольшие Issues после уточнения его контрактов. Завершение этапа — принятое ревью и воспроизводимые результаты на конкретном SHA, а не отчёт модели «всё готово».

| M07 — эксплуатация | M06 | Reload разрешённых настроек, graceful shutdown, лимиты, журналы, метрики и внутренний control service | Некорректный reload не меняет состояние; SIGTERM ограничен; slow client и перегрузка не вызывают безграничный рост |
| M08 — кандидат v0.1 | M07 | systemd, инструкции, артефакт Linux, регрессии, профиль нагрузки и отчёт | Ubuntu 24.04, пилот 10–20 устройств, несколько CPU/NIC, release проверки и ручная проверка владельца |

M02 реализует лимиты, необходимые DNS/connect; M03 и M04 — необходимые пределы сетевых путей; M05 — лимиты auth. M07 объединяет их эксплуатационные настройки и проверяет весь жизненный цикл. Защита ресурсов добавляется вместе с соответствующей функцией.

До M05/M06 сервер используется только на изолированном локальном стенде. Публичный запуск промежуточных версий не является критерием разработки.

## Обязательное развитие после v0.1 и отдельное возможное расширение

| Этап | Содержание | Условие запуска |
| --- | --- | --- |
| M09 — parent proxy / v0.2, ОБЯЗАТЕЛЬНО | HTTP/TLS до родителя, отдельные credentials, egress, CONNECT, loop protection | После v0.1, подробный контракт и отдельное задание; необходимость уже подтверждена |
| M10 — HTTP cache / v0.3, ОБЯЗАТЕЛЬНО | Ограниченный RAM cache; диск — следующий отдельно уточняемый объём | Политика RFC 9111, изоляция и тесты; необходимость cache уже подтверждена |
| M11 — TUI, ОБЯЗАТЕЛЬНО | Локальный API, статус, соединения, users/ACL, конфигурация, ресурсы и egress | Стабильный control service; единая валидация с CLI, работа ядра без UI |
| M12 — локальная web-панель, ВОЗМОЖНО | Тот же API, ориентир 127.0.0.1:7029 | Отдельное решение о реализации, admin auth, Host/Origin/CSRF и тесты |

Реализация parent и cache не отменяется по формулировке «при необходимости». После v0.1 планируются испытания других Linux-дистрибутивов; конкретная матрица уточняется отдельно. Дополнительные задачи: bandwidth limits, квоты трафика, auth backend, ARM64 и пакеты. Они получают собственные решения и задания; не добавляются в реализацию случайно.

## Порядок выдачи заданий

1. Codex уточняет контракты ближайшего этапа, исходя из уже принятого кода.
2. Создаёт Issue с границами, criteria и тестовыми сценариями; перечисляет зависимости и документы.
3. DeepSeek предлагает короткий план, реализует код и тесты, открывает PR.
4. CI проверяет коммит; DeepSeek прикладывает SHA и результаты, включая непрошедшие/пропущенные проверки.
5. Codex проводит ревью; DeepSeek исправляет замечания.
6. Владелец принимает изменение или поручает слияние. Codex обновляет ход разработки и готовит следующее задание.

Детальный план всех будущих файлов не замораживается заранее. Новые сведения о HTTP-клиентах, нагрузке и ограничениях дистрибутива должны корректировать следующие задания через явные решения.

## Критерий готовности v0.1

- Все F01–F11 и N01–N09 имеют проверку либо согласованное документированное исключение.
- Обязательные проверки текущего релизного SHA проходят; неподтверждённые пропуски закрыты.
- Нет открытых блокирующих замечаний по protocol framing, ACL, credentials, resource exhaustion и утечкам.
- Проверены установка, конфигурация, TLS, авторизация, журналирование, остановка и обновление на целевой системе.
- Зафиксированы поддерживаемые протоколы, известные ограничения и результаты нагрузки; заявлений о более высокой скорости, чем Squid, без измерений нет.
- Владелец согласовал выпуск и сценарий первого развёртывания.
